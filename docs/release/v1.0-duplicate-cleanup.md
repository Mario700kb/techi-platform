# V1.0 Duplicate Device Cleanup Guide

## How duplicates are detected

When an agent heartbeats without a known `device_id` or `rustdesk_id`, the backend runs a fingerprint scorer against existing device records. Fields weighted: `hostname`, `local_ip`, `public_ip`, `cpu`, `ram`, `storage`, `domain`, `os_name`, `platform`.

| Confidence | Score | Action taken |
|---|---|---|
| High | ≥ 0.90 | Auto-reuse the existing record (clears duplicate flags) |
| High + active + different RustDesk ID | ≥ 0.90 | Safety-blocked — new record created, flagged as `duplicate_candidate` |
| Medium | 0.70–0.89 | New record created, flagged as `duplicate_candidate` |
| None | < 0.70 | Fresh record, no flag |

A `duplicate_candidate` device is **never automatically deleted or merged**. No data is lost.

## Identifying duplicates in the UI

- **Devices table**: amber `duplicate` badge on any row where `duplicate_candidate = true`.
- **Device Drawer → Overview**: amber warning block showing the primary device number and fingerprint similarity score.

## When to archive a duplicate

Archive a device when:
- It is genuinely a stale re-enrollment of an existing machine (same hostname, same hardware, different agent run).
- The primary record (referenced by `duplicate_of_device_id`) is healthy and actively heartbeating.
- The duplicate has been offline for a meaningful period (stale freshness state).

Do **not** archive when:
- The device might be a real machine that was reimaged or renamed.
- The primary record is also archived or stale — both may need review.
- A human has not verified the match.

## Archiving via the UI (recommended)

1. Open the Device Drawer for the suspected duplicate.
2. Review the similarity score and the referenced primary device.
3. If confident, click **"Archive this duplicate"** (visible only to operators).
4. The device is archived immediately; heartbeats continue to arrive but are flagged in the timeline as `archived_checkin` events.

## Restoring an incorrectly archived device

Use the same Device Drawer → "Restore" button (or the restore action in the devices table actions menu).

## Manual SQL (dev/staging only — never production without a backup)

```sql
-- Find all active duplicate candidates
SELECT id, hostname, duplicate_of_device_id, duplicate_score, last_seen
FROM devices
WHERE duplicate_candidate = 1 AND is_archived = 0
ORDER BY duplicate_score DESC;

-- Archive a specific device by id (replace 42 with real id)
UPDATE devices
SET is_archived = 1,
    archived_at = CURRENT_TIMESTAMP,
    archived_by = 'manual-sql'
WHERE id = 42;
```

Always prefer the UI archive flow. SQL edits bypass activity-event recording and realtime notifications.
